# ADR-003: LLM-Driven Orchestration Strategy

**Status**: Accepted  
**Date**: 2024-04  
**Deciders**: Core team  
**Related**: [ADR-001](ADR-001-memory-architecture.md), [ADR-002](ADR-002-flat-file-storage.md)

---

## Context and Problem Statement

ABM research involves complex, multi-step workflows:
1. Translate research idea → formal model specification
2. Implement specification → executable code
3. Debug code → working simulation
4. Run experiments → interpret results
5. Refine parameters → optimize outcomes
6. Synthesize findings → academic manuscript

Traditional approaches use:
- **Template-based code generation** (rigid, limited expressiveness)
- **Manual coding** (time-consuming, requires programming expertise)
- **Rule-based optimization** (brittle, domain-specific)

Large Language Models (LLMs) offer an alternative: use natural language prompts to orchestrate the entire pipeline. But this raises questions:
- Should the LLM generate code directly, or use templates?
- How much autonomy should the LLM have?
- How do we ensure reproducibility?

---

## Decision Drivers

1. **Flexibility** — Support diverse ABM scenarios (epidemics, markets, social networks)
2. **Accessibility** — Enable non-programmers to conduct ABM research
3. **Quality** — Generate publication-ready code and manuscripts
4. **Reproducibility** — Same input → same output (within stochastic bounds)
5. **Debuggability** — Users should understand what the system is doing

---

## Considered Options

### Option 1: Template-Based Code Generation
Pre-written code templates with placeholders filled by LLM.

**Example**:
```python
# Template: sir_model.py
class SIRAgent(Agent):
    def __init__(self, unique_id, model):
        super().__init__(unique_id, model)
        self.state = "{{ initial_state }}"  # LLM fills this
    
    def step(self):
        if self.state == "S":
            # {{ infection_logic }}  # LLM fills this
```

**Pros**:
- Guaranteed syntactic correctness
- Fast generation (no code synthesis)
- Easy to constrain (templates define structure)

**Cons**:
- Limited expressiveness (can't deviate from templates)
- Template maintenance burden (one per model type)
- Doesn't scale to novel scenarios

### Option 2: Full LLM Code Generation (Selected)
LLM writes complete Python code from scratch based on `DESIGN.md`.

**Example**:
```python
# Generated by LLM from DESIGN.md
class SIRAgent(Agent):
    def __init__(self, unique_id, model):
        super().__init__(unique_id, model)
        self.state = random.choice(["S", "I", "R"], 
                                    p=[0.99, 0.01, 0.0])
    
    def step(self):
        if self.state == "S":
            infected_neighbors = [n for n in self.model.grid.get_neighbors(
                self.pos, moore=True, include_center=False
            ) if n.state == "I"]
            if infected_neighbors:
                if random.random() < self.model.infection_rate:
                    self.state = "I"
```

**Pros**:
- Maximum flexibility (handles novel scenarios)
- No template maintenance
- LLM can apply domain knowledge (e.g., SIR theory)

**Cons**:
- Risk of syntax errors (requires verification phase)
- Harder to constrain (LLM might ignore guidelines)
- Slower generation (more tokens)

### Option 3: Hybrid (Templates + LLM Refinement)
Start with templates, let LLM modify them.

**Pros**:
- Balance between structure and flexibility

**Cons**:
- Complexity of both approaches
- LLM might break template assumptions

---

## Decision Outcome

**Chosen option**: Full LLM code generation (Option 2)

### Rationale

1. **ABM diversity**: No single template covers all scenarios (spatial vs. network, discrete vs. continuous time, homogeneous vs. heterogeneous agents)
2. **Research novelty**: Academic users often explore non-standard models
3. **LLM capability**: Claude Sonnet 4 generates correct Mesa code >90% of the time
4. **Verification phase**: Automated testing + LLM debugging catches errors

### Architecture

```
STORY.md (research narrative)
    ↓
[DesignAgent] — LLM converts to structured spec
    ↓
DESIGN.md (formal specification)
    ↓
[CoderAgent] — LLM generates Mesa code
    ↓
model.py, agent.py, run.py (Python code)
    ↓
[VerifierAgent] — Run tests, fix errors
    ↓
Working simulation
    ↓
[AnalyzerAgent] — LLM interprets results
    ↓
[OptimizerAgent] — LLM proposes next parameters
    ↓
[ReporterAgent] — LLM synthesizes manuscript
```

## Prompt Engineering Strategy

### Phase 1: Design (DesignAgent)

**Input**: `STORY.md` (user's research narrative)  
**Output**: `DESIGN.md` (structured specification)

**Prompt structure**:
```markdown
You are an expert ABM architect. Convert this research story into a formal design.

## Story
{{ story_text }}

## Output Format
# Model Design
## 1. Research Question
## 2. Agents
## 3. Environment
## 4. Processes
## 5. Parameters
## 6. Metrics
```

**Key constraints**:
- Must identify agent types, state variables, and behaviors
- Must specify initialization and scheduling
- Must define measurable outputs

### Phase 2: Code Generation (CoderAgent)

**Input**: `DESIGN.md`  
**Output**: `model.py`, `agent.py`, `run.py`

**Prompt structure**:
```markdown
You are an expert Mesa programmer. Implement this design as Mesa code.

## Design
{{ design_text }}

## Knowledge Base
{{ runtime_framework_guide }}
{{ code_templates }}

## Output
Generate three files:
1. agent.py — Agent classes
2. model.py — Model class with schedule, grid, data collector
3. run.py — Batch runner for parameter sweeps
```

**Key constraints**:
- Must use Mesa API correctly (`mesa.Agent`, `mesa.Model`, `mesa.batch_run`)
- Must implement all processes from DESIGN.md
- Must collect all metrics from DESIGN.md

### Phase 3: Verification (VerifierAgent)

**Input**: Generated code + error logs  
**Output**: Fixed code or failure report

**Prompt structure**:
```markdown
The generated code failed with this error:

{{ error_traceback }}

## Code
{{ model_py }}

## Task
Fix the error. Output the corrected file.
```

**Key constraints**:
- Max 3 retries per error
- Must preserve original design intent
- Must not introduce new bugs

### Phase 5: Analysis (AnalyzerAgent)

**Input**: Simulation output (CSV)  
**Output**: Natural language insights

**Prompt structure**:
```markdown
Analyze this simulation output:

{{ metrics_csv }}

## Context
- Parameters: {{ params }}
- Hypothesis: {{ hypothesis }}

## Task
Provide insights: What patterns emerged? Did results match expectations?
```

### Phase 6: Optimization (OptimizerAgent)

**Input**: Memory context (working + episodic + semantic)  
**Output**: Next parameter values

**Prompt structure**:
```markdown
## Experiment History
{{ memory_context }}

## Current Hypothesis
{{ hypothesis }}

## Task
Propose next parameter values to test. Explain your reasoning.
```

**Key constraints**:
- Must stay within parameter bounds
- Must justify choices based on prior runs
- Must avoid redundant experiments

### Phase 7: Reporting (ReporterAgent)

**Input**: All iterations + ODD protocol + sensitivity analysis  
**Output**: Academic manuscript

**Prompt structure**:
```markdown
Synthesize this ABM research into a publication-ready manuscript.

## Story
{{ story }}

## Design
{{ design }}

## ODD Protocol
{{ odd }}

## Results ({{ n_iterations }} iterations)
{{ all_runs_summary }}

## Sensitivity Analysis
{{ sensitivity_results }}

## Output Format
5000-7000 word manuscript with:
1. Introduction
2. Methods (ODD)
3. Results
4. Discussion
5. Conclusion
6. References
```

## Consequences

### Positive

✅ **Flexibility**: Handles diverse ABM scenarios without templates  
✅ **Accessibility**: Non-programmers can conduct research via natural language  
✅ **Quality**: LLM applies domain knowledge (e.g., SIR theory, network effects)  
✅ **Iteration speed**: Automated debugging reduces manual intervention  
✅ **Manuscript quality**: LLM synthesizes coherent narratives from raw data

### Negative

⚠️ **Non-determinism**: Same prompt → slightly different code (LLM sampling)  
⚠️ **Verification overhead**: ~10% of generations require debugging  
⚠️ **Token cost**: Full code generation uses more tokens than templates  
⚠️ **Black-box risk**: Users may not understand generated code

### Risks

🔴 **Hallucinated APIs**: LLM invents non-existent Mesa methods  
**Mitigation**: Inject Mesa API reference into prompts, verify imports

🔴 **Logic errors**: Code runs but implements wrong behavior  
**Mitigation**: Sanity checks (agent count, metric ranges), ODD cross-validation

🔴 **Prompt injection**: Malicious `STORY.md` manipulates LLM  
**Mitigation**: Sanitize user input, use structured prompts

🔴 **Cost explosion**: Large experiments → many LLM calls  
**Mitigation**: Cache repeated prompts, use cheaper models for verification

## Reproducibility Strategy

### Deterministic Elements

✅ **Random seeds**: User can specify `--seed 42` for reproducible simulations  
✅ **Parameter logs**: All runs recorded in `episodic.jsonl`  
✅ **Code snapshots**: Generated code saved in workspace  
✅ **Prompt templates**: Fixed templates in `abm_auto/prompts/`

### Non-Deterministic Elements

⚠️ **LLM sampling**: Temperature > 0 → different outputs  
⚠️ **API updates**: Claude model updates may change behavior  
⚠️ **Optimization paths**: LLM may explore parameters in different order

### Reproducibility Levels

| Level | Guarantee | How to Achieve |
|-------|-----------|----------------|
| **Simulation** | Same params → same results | Use `--seed` flag |
| **Code** | Same design → same code | Pin LLM model version, temperature=0 |
| **Optimization** | Same trajectory | Save/replay episodic memory |
| **Full pipeline** | Same manuscript | Archive entire workspace |

**Recommendation**: For publication, archive the workspace directory (includes all code, data, and memory).

## Alternatives Considered But Rejected

### DSL (Domain-Specific Language)
Define a custom language for ABM, compile to Python.

**Reason**: High development cost, limited adoption, doesn't leverage LLM strengths

### No-Code GUI
Visual programming interface (drag-and-drop agents, behaviors).

**Reason**: Less expressive than natural language, harder to version control

### Jupyter Notebooks
Interactive notebooks with LLM-generated cells.

**Reason**: Doesn't support autonomous multi-iteration loops, harder to automate

## Future Enhancements

**Potential Improvements** (not yet implemented):

1. **Code review agent**: LLM reviews generated code for best practices
2. **Multi-model ensemble**: Generate 3 implementations, pick best via voting
3. **Incremental refinement**: LLM edits existing code instead of rewriting
4. **User feedback loop**: Allow manual corrections, learn from them
